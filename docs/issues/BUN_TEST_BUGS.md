## Bug 1: `NO_COLOR` 環境變數不影響 snapshot 輸出 / `NO_COLOR` environment variable does not affect snapshot output

**問題 / Issue**：`NO_COLOR=1` 環境變數無法影響 `toThrowErrorMatchingSnapshot()` 生成的 snapshot 內容。 / The `NO_COLOR=1` environment variable does not affect the snapshot content generated by `toThrowErrorMatchingSnapshot()`.

當使用 `--env-file=.env.test` 載入環境變數時，測試本身可以讀取到 `NO_COLOR=1`，但 `toThrowErrorMatchingSnapshot()` 輸出的錯誤訊息仍然包含 ANSI 顏色代碼。 / When using `--env-file=.env.test` to load environment variables, the test itself can read `NO_COLOR=1`, but the error message output by `toThrowErrorMatchingSnapshot()` still contains ANSI color codes.

**環境 / Environment**：Bun: 1.3.10+, Windows 11

**重現步驟 / Steps to reproduce**：

1. 建立 `.env.test` 檔案 / Create `.env.test` file：
```env
NO_COLOR=1
FORCE_COLOR=0
```

2. 使用 `--env-file` 執行測試 / Run tests with `--env-file`：
```bash
bun --env-file=.env.test test --update-snapshots
```

3. 檢查 snapshot 檔案，會發現仍然包含 ANSI 顏色代碼 / Check the snapshot file - it will still contain ANSI color codes：
```snap
exports[`...`] = `
"\x1B[2mexpect(\x1B[0m\x1B[31mreceived\x1B[0m\x1B[2m).\x1B[0mtoMatchObject\x1B[2m(\x1B[0m\x1B[32mexpected\x1B[0m\x1B[2m)\x1B[0m
...
```

**Workaround**：使用 `cross-env` 在命令列明確設置環境變數 / Use `cross-env` to explicitly set environment variables in the command line：
```json
{
  "scripts": {
    "test": "cross-env NO_COLOR=1 FORCE_COLOR=0 bun --env-file=.env.test test --update-snapshots"
  }
}
```

## Bug 2: `toMatchObject` 與 spread operator 和 `expect.any()` 的問題 / `toMatchObject` fails with spread operator and `expect.any()`

**問題 / Issue**：當使用三元運算子展開 `expect.any()` 時，Bun 的 `toMatchObject` 無法正確處理。 / Bun's `toMatchObject` fails to handle `expect.any()` when used with ternary spread operator.

**環境 / Environment**：Bun: 1.3.10+, Jest: 行為正確（預期行為）/ Works correctly (expected behavior)

### 正常情況（不使用 `...`）/ Working case (without spread operator)

```typescript
it("正常運作 / works", () => {
    const actual = {
        name: "test name",
        extra: "test extra",
    };

    // 直接內聯使用 expect.any() / Direct inline use of expect.any()
    const expected = {
        name: "test",
        extra: expect.any(String),
    };

    expect(actual).toMatchObject(expected);  // ✅ 成功 / Works
});
```

### 失敗情況（使用三元展開 `...`）/ Failing case (with spread operator `...`)

```typescript
it("失敗 / fails", () => {
    const hasExtra = true;

    const actual = {
        name: "test name",
        extra: "test extra",
    };

    // 透過三元展開使用 expect.any() / Uses expect.any() through ternary spread
    const expected = {
        name: "test",
        ...(hasExtra ? { extra: expect.any(String) } : {}),
    };

    // 預期：應成功（Jest 中正常）/ Expected: Should succeed (works in Jest)
    // 實際：失敗 / Actual: Fails
    expect(actual).toMatchObject(expected);  // ❌ 失敗 / Fails
});
```

### 錯誤輸出 / Error output

```
"expect(received).toMatchObject(expected)

  {
-   "extra": Any<String>,
-   "name": "test",
+   "extra": "test extra",
+   "name": "test name",
  }

- Expected  - 2
+ Received  + 2
"
```

### Workaround

避免在三元展開中使用 `expect.any()`，改為直接內聯 / Avoid using `expect.any()` in ternary spread, use inline instead：

```typescript
// ❌ 失敗 / Fails
const expected = {
    name: "test",
    ...(hasExtra ? { extra: expect.any(String) } : {}),
};

// ✅ 成功 / Works
const expected = {
    name: "test",
    extra: expect.any(String),  // 直接內聯，不使用三元展開 / Inline, no ternary spread
};
```

**問題 / Issue**：嘗試使用 `Object.freeze()` 來解決 Bug 2 會失敗。 / Attempting to use `Object.freeze()` to fix Bug 2 also fails.

**環境 / Environment**：Bun: 1.3.10+

## Bug: "toMatchObject with expect.any"

**問題 / Issue**：`toMatchObject` 會修改傳入的 actual 物件！將匹配到的屬性替換為空的 matcher 物件 `{}`。 / `toMatchObject` mutates the actual object! It replaces matched properties with an empty matcher object `{}`.

**來源 / Source**：https://github.com/oven-sh/bun/issues/3521

**環境 / Environment**：Bun: 1.3.10+, Jest: 行為正確（不應修改 actual）/ Works correctly (should not modify actual)

### Mutation 證據 / Mutation Evidence

```typescript
const obj = {
    foo: "foo",
    bar: "bar",
};

console.log("Before:", JSON.stringify(obj));
// Before: {"foo":"foo","bar":"bar"}

expect(obj).toMatchObject({
    bar: expect.any(String),
});

console.log("After:", JSON.stringify(obj));
// After: {"foo":"foo","bar":{}}
//                        ^^ 被替換成空物件！/ Replaced with empty object!
```

### 失敗案例 / Failing Case

```typescript
it("toMatchObject mutates actual", () => {
    const obj = {
        foo: "foo",
        bar: "bar",
    };

    // 第一次 toMatchObject 後，obj.bar 被替換成 {}
    // After first toMatchObject, obj.bar is replaced with {}
    expect(obj).toMatchObject({
        bar: expect.any(String),
    });

    // 這就是為什麼第二次 toMatchObject 會失敗
    // This is why the second toMatchObject fails
    expect(obj).toMatchObject({
        bar: expect.any(String),
    });
});
```

### 錯誤輸出 / Error Output

```
error: expect(received).toMatchObject(expected)

@@ -2,3 +2,3 @@
   "bar": Any<String>,
+   "foo": "foo",
 }

- Expected  - 0
+ Received  + 1
```

### Workaround: 使用 `{...config}` 防止 Mutation

使用 `{...config}` 而非直接使用 `config` 是為了防止 `toMatchObject` 修改原物件！

```typescript
/**
 * 測試工具配置條目
 * Test tool configuration entry
 *
 * ⚠️ Workaround for Bun "toMatchObject with expect.any" BUG:
 *
 * 使用 `{...config}` 而非直接使用 `config` 是為了防止 toMatchObject 修改 config 物件！
 *
 * Bun 的 toMatchObject 會修改傳入的 actual 物件，
 * 將匹配到的屬性替換為空的 matcher 物件 {}。
 * 這會導致後續的測試失敗，因為 config 的成員已被永久修改。
 */
function _testAriseToolsConfigEntry(config: typeof ARISE_TOOLS[EnumAriseTools])
{
    const hasDescription = typeof (config as any).description !== 'undefined';

    // ⚠️ 使用 {...config} 防止 toMatchObject 修改原物件
    // ⚠️ Use {...config} to prevent toMatchObject from modifying the original object
    expect({
        ...config,
    }).toMatchObject(hasDescription ? {
        description: expect.any(String),
        shortDescription: expect.any(String),
        args: expect.anything(),
    } : {
        shortDescription: expect.any(String),
        args: expect.anything(),
    });
}
```

**為什麼 `{...config}` 可以防止 Mutation？**

| 方法 | 是否防止 Mutation |
|------|-----------------|
| `expect(config).toMatchObject(...)` | ❌ 否 - 直接修改原物件 |
| `expect({...config}).toMatchObject(...)` | ✅ 是 - spread 創建新物件 |

`{...config}` 會創建一個新的物件，指向相同的值。因此當 `toMatchObject` 修改新物件時，原物件不受影響。

## Bug: "toMatchInlineSnapshot with bad string literal"

**問題 / Issue**：`toMatchInlineSnapshot` 必須傳入字面量字串，無法使用 `JSON.stringify()` 等動態方式生成期望值。 / `toMatchInlineSnapshot` requires a string literal argument, cannot use dynamic expressions like `JSON.stringify()`.

**環境 / Environment**：Bun: 1.3.10+

### 隱形 BUG / Hidden BUG

⚠️ **嚴重性**：這個 BUG 不只是單個測試失敗，而是會導致**測試框架崩潰**！

- 當測試執行時：`ELIFECYCLE Test failed` 出現在測試結果底部
- 當測試 skip 時：所有測試正常通過

對比：`toMatchObject with expect.any` 的 BUG 可以被正常捕捉（不會崩潰），但 `toMatchInlineSnapshot with bad string literal` 的 BUG 會導致框架崩潰。

### 失敗案例 / Failing Case

```typescript
it("toMatchInlineSnapshot 失敗 / fails", () => {
    const actual = { foo: "foo", bar: "bar" };

    // ❌ 錯誤：Argument must be a string literal
    expect(actual).toMatchInlineSnapshot(JSON.stringify({
        foo: "foo",
        bar: "bar",
    }));
});
```

### 錯誤輸出 / Error Output

```
error: Failed to update inline snapshot: Argument must be a string literal
```

### 測試追蹤 / Test Tracing

使用 `console.log` 追蹤執行流程：

```
a-001 ~ a-005    ✓ (正常印出)
a-006, a-007     ✓ (正常印出，屬於 toMatchSnapshot)
[start] a-008    ✓ (正常印出)
❌ BUG happen!   ← 錯誤發生 (expect with toMatchInlineSnapshot)
[end] a-009      ✓ (仍然印出！BUG 後的 log 仍然執行)
[start] a-010    ✓ (正常印出)
❌ BUG happen!   ← 錯誤發生 (第一個 expect with toMatchInlineSnapshot)
a-011            ✓ (仍然印出)
❌ BUG happen!   ← 錯誤發生 (第二個 expect with toMatchInlineSnapshot)
[end] a-012      ✓ (仍然印出！BUG 後的 log 仍然執行)
a-013, a-014     ✓ (正常印出)
```

### BUG 位置總結 / BUG locations summary

| BUG | 位置 | 程式碼 |
|-----|------|--------|
| **BUG 1** | [start] a-008 之後 | `expect({...}).toMatchInlineSnapshot(JSON.stringify({...}))` |
| **BUG 2** | [start] a-010 之後 | `expect(`"..."`).toMatchInlineSnapshot(JSON.stringify({...}))` |
| **BUG 3** | a-011 之後 | `expect(() => { expect(`"..."`).toMatchInlineSnapshot(JSON.stringify({...})) }).not.toThrow()` |

### ⚠️ BUG 3 的特殊之處 / Special behavior of BUG 3

不論是 `).not.toThrow();` or `).toThrow();` 或不管有沒有在 `expect(() => { ... })` 裡面都會發生 BUG！

Whether it's `).not.toThrow();` or `).toThrow();` or whether it's inside `expect(() => { ... })` or not, the BUG will occur!

### 結論 / Conclusion

1. BUG 發生在 toMatchInlineSnapshot 使用 JSON.stringify() 作為參數時
2. BUG 發生時，測試框架進入錯誤狀態
3. 但奇怪的是，後續的 console.log() 仍然會執行！
4. 這表明 BUG 不是發生在 JavaScript 執行層面，而是在測試框架更新 snapshot 的層面

1. BUG occurs when toMatchInlineSnapshot uses JSON.stringify() as argument
2. When BUG occurs, test framework enters error state
3. But surprisingly, subsequent console.log() still executes!
4. This suggests the BUG is not at JavaScript execution level, but at test framework's snapshot update level
